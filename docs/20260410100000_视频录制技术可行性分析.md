# 视频录制功能技术可行性分析

## 需求

在现有 GIF 录制基础上，新增视频录制能力：
- 高清画质 + 小文件体积
- 可控制视频质量（分辨率、码率、帧率）
- 选区录制（和 GIF 一样的交互）
- 跨平台（Windows / macOS / Linux）

---

## 候选方案全景

### 方案 A：内嵌 FFmpeg 静态库

| 维度 | 说明 |
|------|------|
| 原理 | 通过 Rust FFI 调用 FFmpeg 的 libavcodec/libavformat 进行 H.264/H.265 编码 |
| Rust crate | `ffmpeg-next`（FFmpeg 的 Rust 绑定） |
| 编码格式 | H.264（兼容性最好）/ H.265（压缩率更高） |
| 容器格式 | MP4 |
| 画质 | 极好，工业级编码器 |
| 压缩率 | 极高，30s 1080p 约 2-5MB（H.264 CRF 23） |
| **包体积增量** | **+15-25MB**（FFmpeg 静态链接，含 x264 编码器） |
| 编译复杂度 | 高，需要交叉编译 FFmpeg（Windows 需要 MSYS2/vcpkg，macOS 需要 homebrew） |
| 优点 | 功能最强，支持所有编码参数调优 |
| 缺点 | 包体积大幅膨胀，编译链路复杂，CI 构建时间翻倍 |

### 方案 B：调用系统自带 FFmpeg

| 维度 | 说明 |
|------|------|
| 原理 | 先把帧保存为图片序列，再调用系统安装的 `ffmpeg` 命令行编码 |
| 依赖 | 用户系统需要安装 FFmpeg（`choco install ffmpeg` / `brew install ffmpeg`） |
| 编码格式 | 任意（取决于系统 FFmpeg 版本） |
| **包体积增量** | **0MB**（不内嵌任何东西） |
| 编译复杂度 | 极低，只需 `std::process::Command` |
| 优点 | 零体积增长，实现简单 |
| 缺点 | **用户必须自己装 FFmpeg**，不符合"双击即用"的产品定位 |

### 方案 C：纯 Rust 编码器（openh264）

| 维度 | 说明 |
|------|------|
| 原理 | 用纯 Rust 实现的视频编码 crate，不依赖 FFmpeg |
| 候选 crate | `openh264`（思科开源 H.264 编码器的 Rust 绑定）|
| 编码格式 | H.264 Baseline/Main Profile |
| 容器格式 | MP4（用 `mp4` 或 `minimp4` crate 封装） |
| 画质 | 良好（不如 x264 但完全够用） |
| 压缩率 | 好，30s 1080p 约 5-10MB |
| **包体积增量** | **+2-4MB**（openh264 动态库约 2MB，或静态链接 ~4MB） |
| 编译复杂度 | 低，`openh264` 会自动下载预编译二进制 |
| 优点 | 体积小，编译简单，不依赖外部工具，跨平台 |
| 缺点 | 编码速度和压缩率不如 x264，不支持 H.265 |

### 方案 D：平台原生编码器

| 维度 | 说明 |
|------|------|
| 原理 | 调用系统自带的硬件/软件编码器 |
| Windows | Media Foundation（H.264 硬件加速） |
| macOS | VideoToolbox（H.264/H.265 硬件加速） |
| Linux | VA-API / NVENC（需要驱动支持） |
| **包体积增量** | **0MB**（调用系统 API） |
| 编译复杂度 | 高，每个平台完全不同的 API，三套代码 |
| 优点 | 零体积，硬件加速性能最好，系统原生 |
| 缺点 | 三平台三套实现，维护成本极高 |

### 方案 E：FFmpeg 按需下载（用户侧下载）

| 维度 | 说明 |
|------|------|
| 原理 | 安装包不内嵌 FFmpeg，首次使用视频录制时提示用户下载，存到 `~/.sip-cc/bin/` |
| 编码格式 | 任意（x264/x265/AV1 取决于下载的 FFmpeg 版本） |
| **包体积增量** | **0MB**（不内嵌） |
| 用户侧存储 | ~30MB（一次性下载） |
| 编译复杂度 | 最低（`std::process::Command` 调用命令行） |
| 优点 | 安装包零膨胀，编码质量最好，全参数可控，维护最简单 |
| 缺点 | 首次使用需下载一次 |

## 决策记录

### 决策 1：选择方案 E（FFmpeg 按需下载）作为主方案

**决策理由**：

1. **安装包零膨胀**：sip-cc 定位"极致小"，当前安装包 ~8MB。方案 A 会增加 15-25MB（翻倍），不可接受。方案 C 增加 2-4MB 可以接受但不是最优。方案 E 安装包 0 增量。

2. **编码质量最好**：FFmpeg 的 x264 编码器是工业级标准，画质和压缩率远超 openh264。用户对"高清又小"有明确诉求，x264 CRF 模式天然满足。

3. **参数灵活度最高**：FFmpeg 支持 CRF/preset/tune/分辨率/码率/帧率等全部参数。openh264 只能控制基础参数。未来如果用户需要 H.265 或 AV1，FFmpeg 天然支持，openh264 不行。

4. **维护成本最低**：Rust 端只需要 `std::process::Command` 调用命令行，不引入任何编码相关依赖。编码逻辑全在 FFmpeg 里，FFmpeg 的 bug 和更新跟我们无关。

5. **编译最简单**：不需要交叉编译 FFmpeg（方案 A 的噩梦），不需要三套平台代码（方案 D），CI 构建零变化。

**对"首次需下载"的评估**：
- 下载量约 30MB，在当代网络环境下 10-30 秒完成
- 只需下载一次，后续永久使用
- 截屏和 GIF 录制完全不受影响（不装 FFmpeg 也能用）
- 同类产品（yt-dlp、OBS 便携版、HandBrake 便携版）都采用类似策略，用户接受度高

**为什么不选其他方案**：
- **方案 A（FFmpeg 内嵌）**：包体积 +15-25MB，违背"极致小"定位；编译链路复杂，CI 维护成本高
- **方案 B（系统 FFmpeg）**：要求用户自己装 FFmpeg + 配 PATH，违背"双击即用"原则
- **方案 C（openh264）**：画质不如 x264，不支持 H.265，参数有限。作为备选保留
- **方案 D（原生编码）**：三平台三套 API（Media Foundation / VideoToolbox / VA-API），维护成本极高，得不偿失

### 决策 2：没有 FFmpeg 就不能录视频（硬依赖）

**决策理由**：

1. **简化逻辑**：不搞"有 FFmpeg 用 FFmpeg，没有用内置编码器"的降级策略。两条代码路径意味着两倍的测试和维护成本。

2. **用户预期一致**：要么能录高质量视频，要么明确告诉用户"需要下载"。不搞降级版本，避免用户困惑"为什么我的视频质量比别人差"。

3. **不影响核心功能**：截屏和 GIF 录制是 sip-cc 的核心能力，完全不依赖 FFmpeg。视频录制是增值功能，按需启用合理。

4. **用户引导明确**：弹窗只有两个选择——下载或取消。没有"使用低质量内置编码器"的选项，决策路径最短。

### 决策 3：两阶段录制（帧序列 → 编码）

**决策理由**：

1. **最简单可靠**：FFmpeg 命令行实时流式输入需要 pipe 或命名管道，跨平台兼容性差（Windows 命名管道和 Unix 不同）。帧序列方式只需要写文件 + 调命令，零平台差异。

2. **最大复用**：帧捕获逻辑和 GIF 录制 90% 相同（`capture_region → 保存帧`），只是 GIF 保存到 encoder，视频保存到文件。

3. **编码参数更灵活**：帧序列方式可以在编码阶段随意调整参数（帧率、CRF、分辨率缩放），不需要在录制时就确定。

4. **临时空间可接受**：30s × 15fps × ~200KB/帧 ≈ 90MB 临时空间，编码完立即清理。现代磁盘不是瓶颈。

### 备选方案保留

> 如果未来发现 FFmpeg 下载方案有不可克服的问题（比如某些地区网络完全无法下载、企业内网严格限制外部下载），可以考虑内嵌 `openh264 + minimp4` 作为轻量备选：
> - `openh264`：Cisco 开源 H.264 编码器，Rust 绑定，自动下载预编译库
> - `minimp4`：纯 Rust MP4 容器封装
> - 体积增量仅 +2-3MB，画质和参数灵活度不如 FFmpeg
> - 实施成本低，可以在一天内完成
>
> 此方案暂不实施，仅记录为后备。如需启用，参考方案 C 的技术设计即可。

## 最终方案：FFmpeg 按需下载

### 核心思路

安装包不内嵌 FFmpeg，用户首次使用视频录制时自动提示下载。FFmpeg 存放在 `~/.sip-cc/bin/` 下，不污染系统环境。

**没有 FFmpeg = 无法录制视频**，截屏和 GIF 录制不受影响。

### 用户体验流程

```
用户点击「录制视频」（托盘菜单或快捷键）
  │
  ├─ 检查 ~/.sip-cc/bin/ffmpeg(.exe) 是否存在
  │
  ├─ 不存在 → 弹窗提示
  │   ┌──────────────────────────────────────┐
  │   │  视频录制需要 FFmpeg 支持             │
  │   │                                      │
  │   │  FFmpeg 是开源视频编码工具，           │
  │   │  首次使用需下载（约 30MB），           │
  │   │  下载后自动配置，无需手动安装。         │
  │   │                                      │
  │   │          [下载并启用]    [取消]        │
  │   └──────────────────────────────────────┘
  │              │
  │              ├─ 用户确认 → 后台下载 → 解压到 ~/.sip-cc/bin/ → 下载完成后自动打开选区
  │              └─ 用户取消 → 不录制，回到正常状态
  │
  └─ 存在 → 直接打开选区遮罩 → 选区 → 录制 → 调用 ffmpeg 编码 → 输出 MP4
```

## 技术设计

### FFmpeg 管理

#### 存放位置

```
~/.sip-cc/
├── config.json
├── logs/
└── bin/
    ├── ffmpeg.exe          # Windows
    ├── ffmpeg              # macOS / Linux
    └── ffmpeg.version      # 记录版本号，用于升级检测
```

#### 下载源

| 平台 | 来源 | 文件 | 大小 |
|------|------|------|------|
| Windows | gyan.dev | `ffmpeg-release-essentials.zip` | ~30MB |
| macOS | evermeet.cx | `ffmpeg-7.x.zip` | ~25MB |
| Linux | johnvansickle.com | `ffmpeg-release-amd64-static.tar.xz` | ~30MB |

锁定特定版本号（如 7.1），避免版本不一致。

#### 下载流程（Rust 端）

```rust
pub async fn ensure_ffmpeg(app: &AppHandle) -> Result<PathBuf, String> {
    let ffmpeg_path = get_ffmpeg_path();
    
    if ffmpeg_path.exists() {
        return Ok(ffmpeg_path);
    }
    
    // 弹窗提示用户确认下载
    // 用户确认后：
    // 1. 下载压缩包到临时目录（带进度回调）
    // 2. 解压出 ffmpeg 可执行文件
    // 3. 移动到 ~/.sip-cc/bin/
    // 4. 设置可执行权限（macOS/Linux）
    // 5. 写入 ffmpeg.version 文件
    
    Ok(ffmpeg_path)
}

fn get_ffmpeg_path() -> PathBuf {
    let bin_dir = ConfigManager::base_dir().join("bin");
    if cfg!(target_os = "windows") {
        bin_dir.join("ffmpeg.exe")
    } else {
        bin_dir.join("ffmpeg")
    }
}
```

#### 下载失败兜底

- 网络超时：重试 3 次，每次间隔 3 秒
- 下载中断：支持断点续传（HTTP Range 请求）
- 解压失败：清理临时文件，提示用户重试
- 多镜像源：主源失败自动切换备用源
- 最终兜底：提示用户手动下载并放入 `~/.sip-cc/bin/`

### 录制流程

#### 两阶段录制

```
阶段 1：帧捕获（和 GIF 一样）
  录制线程循环 capture_region() → 保存为 PNG 序列到临时目录
  ~/.sip-cc/tmp/video_20260410_120000/
    ├── frame_000001.png
    ├── frame_000002.png
    └── ...

阶段 2：编码（录制停止后）
  调用 ffmpeg 命令将图片序列编码为 MP4：
  ffmpeg -framerate 15 -i frame_%06d.png -c:v libx264 -crf 23 -preset medium -pix_fmt yuv420p output.mp4
  编码完成后删除临时帧文件
```

#### FFmpeg 编码参数

```bash
ffmpeg \
  -framerate {video_fps} \               # 帧率
  -i {tmp_dir}/frame_%06d.png \          # 输入帧序列
  -c:v libx264 \                         # H.264 编码器
  -crf {crf_value} \                     # 质量控制（0-51，越小越好，23 是默认）
  -preset {preset} \                     # 编码速度/压缩率平衡
  -pix_fmt yuv420p \                     # 像素格式（兼容性最好）
  -movflags +faststart \                 # MP4 快速启动（metadata 前置）
  {output_path}
```

#### 质量预设

| 预设 | 帧率 | CRF | preset | 30s 1080p 估计大小 |
|------|------|-----|--------|-------------------|
| 低（体积优先） | 10 fps | 28 | fast | ~2MB |
| 中（均衡） | 15 fps | 23 | medium | ~5MB |
| 高（画质优先） | 30 fps | 18 | slow | ~15MB |

### 可控参数

config.json 扩展：

```json
{
  "video_fps": 15,
  "video_crf": 23,
  "video_preset": "medium",
  "video_max_duration_secs": 300
}
```

| 参数 | 说明 | 范围 | 默认值 |
|------|------|------|--------|
| `video_fps` | 录制帧率 | 5-60 | 15 |
| `video_crf` | 质量因子（越小越清晰，文件越大） | 0-51 | 23 |
| `video_preset` | 编码速度预设 | ultrafast/fast/medium/slow | medium |
| `video_max_duration_secs` | 最大录制时长（秒） | 1-600 | 300 |

## 风险评估

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| FFmpeg 下载源不可用 | 无法下载 | 低 | 多镜像源 + 手动下载引导 |
| 网络限制（公司内网） | 下载失败 | 中 | 提供手动下载链接 + 放置路径说明 |
| 临时帧文件占磁盘 | 磁盘空间不足 | 低 | 预检剩余空间，不足时警告 |
| FFmpeg 进程崩溃 | 编码失败 | 低 | 检查 exit code + stderr 输出给用户 |
| macOS FFmpeg 签名 | 无法执行 | 中 | 自动 `chmod +x` + `xattr -cr` |
| 帧率和实际捕获速度不匹配 | 视频变速 | 中 | 记录实际帧时间戳，编码时用 `-vsync cfr` |
