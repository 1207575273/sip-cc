# Release 二进制体积优化分析

> 状态：**仅分析存档，未采纳**。记录结论供后续参考。

## 问题

v0.8.0 引入视频录制功能后，Windows release 二进制从 ~8MB 增长到 ~20MB。

## 原因定位

体积增长来自 FFmpeg 按需下载功能引入的网络/解压依赖，**与单元测试无关**（`#[cfg(test)]` 不参与 release 编译）。

| 依赖 | 用途 | 估算体积贡献 |
|------|------|-------------|
| `reqwest` + `rustls-tls` | HTTP 下载 + TLS | 3-5MB（ring 加密库、rustls、webpki 根证书） |
| `sevenz-rust2` | Windows .7z 解压 | ~1MB |
| `zip` | macOS/Linux .zip 解压 | ~0.5MB |
| `futures-util` | 异步流式下载 | ~0.5MB |

## 优化方案（已验证，未采纳）

在 `Cargo.toml` 中添加：

```toml
[profile.release]
lto = true          # 链接时优化，跨 crate 消除死代码
codegen-units = 1   # 单编译单元，更彻底的优化
strip = true        # 移除符号表和调试信息
opt-level = "s"     # 优化目标偏向体积（"s"=size, "z"=更激进的size）
```

### 验证结果

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| `sip-cc.exe` 体积 | 20MB | 12MB | -40% |
| release 编译时间 | ~1.5min | ~7.5min | +5x |

### 未采纳原因

- CI 编译时间从 ~1.5 分钟涨到 ~7.5 分钟，四平台并行总耗时明显增加
- 12MB vs 20MB 差距在可接受范围内，用户下载的是压缩包（zip/dmg/msi），实际下载体积差距更小
- `codegen-units = 1` 可能在极端场景下影响运行时性能（虽然理论上应该更快）
- 当前阶段优先开发效率，CI 反馈速度比打包体积更重要

### 后续可选择性启用

如果未来体积成为问题（比如超过 30MB），可以逐项启用：

1. **优先启用 `strip = true`**：零副作用，减 2-3MB，不影响编译时间
2. **其次 `lto = "thin"`**：比 `lto = true` 快很多，效果接近（减 ~30%）
3. **最后 `codegen-units = 1` + `opt-level = "s"`**：收益递减，编译代价最大

也可以考虑：
- `reqwest` 换用 `native-tls` feature（复用系统 TLS 库，减少 rustls 体积，但牺牲跨平台一致性）
- FFmpeg 下载改用系统 `curl`/`Invoke-WebRequest`（完全消除 reqwest 依赖，但增加平台适配代码）
