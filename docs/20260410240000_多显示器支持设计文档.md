# 多显示器支持设计文档

> 版本：v2.0 | 日期：2026-04-10 | 作者：codeYang

---

## 一、背景与目标

### 1.1 现状

sip-cc 当前所有截屏、GIF 录制、视频录制功能仅支持**主显示器**。核心瓶颈：

| 瓶颈点 | 文件 | 具体代码 |
|--------|------|----------|
| 屏幕捕获只取主显示器 | `snap/capture.rs` | `get_primary_monitor()` 通过 `is_primary()` 过滤 |
| DPI 缩放只读主显示器 | `commands/snap_cmd.rs` | `get_scale_factor()` 调用 `app.primary_monitor()` |
| overlay 窗口只覆盖主显示器 | `commands/snap_cmd.rs` | `show_overlay()` 用 `fullscreen(true)` 或主显示器尺寸 |
| 屏幕逻辑尺寸只算主显示器 | `commands/snap_cmd.rs` | `get_screen_logical_size()` 调用 `app.primary_monitor()` |

### 1.2 目标

- 用户拥有多个显示器时，可以在**任意显示器**上进行截屏、GIF 录制、视频录制
- **Windows/Linux 支持跨屏选区**：选区可以横跨多个显示器（对标 PipinX 体验）
- 三大平台（Windows、macOS、Linux）均支持
- 对现有单显示器用户无感知，行为完全向后兼容

### 1.3 不做的事情（YAGNI）

- **macOS 不支持跨屏选区**：方案 B 每屏独立 overlay，选区限定在单个显示器内（CleanShot X、Shottr 同样如此）
- **不处理录制过程中显示器热插拔**：开始录制后显示器配置变化属于极端边界情况
- **不支持不同显示器独立的帧率/质量配置**：复杂度收益比太低

---

## 二、核心策略：平台分治

### 2.1 方案对比

| 维度 | 方案 A：单 overlay 覆盖虚拟桌面 | 方案 B：每个显示器一个 overlay |
|------|-------------------------------|-------------------------------|
| 原理 | 计算所有显示器的 bounding box，创建一个大窗口覆盖整个虚拟桌面 | 枚举所有显示器，每个创建独立的 overlay 窗口 |
| 跨屏选区 | 天然支持，**本次要做** | 不支持（macOS 可接受） |
| DPI 混合处理 | WebView 只有一个 devicePixelRatio，混合 DPI 时坐标偏移 | 每个窗口独立 DPI，无问题 |
| 实现复杂度 | 低 | 中等 |
| Windows 适配 | 虚拟桌面天然支持，最自然 | 也可行但没必要 |
| macOS 适配 | Retina + 非 Retina 混用时有坐标偏移风险 | 完美处理 |

### 2.2 决策

```
Windows / Linux → 方案 A（单 overlay 覆盖虚拟桌面）
macOS           → 方案 B（每个显示器一个 overlay）
```

**决策依据**：

- **Windows/Linux**：虚拟桌面坐标系统一，多显示器 DPI 差异较少（Windows 在 DPI 虚拟化层面做了处理），单 overlay 最自然且改动最小
- **macOS**：MacBook Retina（2x）+ 外接非 Retina（1x）是非常常见的场景，WebView 跨屏时 `devicePixelRatio` 只取一个值会导致坐标错位，每屏独立 overlay 彻底规避此问题
- 现有代码已经有 `cfg!(target_os = "macos")` 的平台分支，增加分治成本可控

**`capture_virtual_screen()` 拼接逻辑：**

```rust
pub fn capture_virtual_screen() -> Result<(RgbaImage, VirtualScreenBounds), String> {
    let monitors = get_all_monitors()?;

    // 1. 计算 bounding box
    let min_x = monitors.iter().map(|m| m.x()).min().unwrap_or(0);
    let min_y = monitors.iter().map(|m| m.y()).min().unwrap_or(0);
    let max_x = monitors.iter().map(|m| m.x() + m.width() as i32).max().unwrap_or(0);
    let max_y = monitors.iter().map(|m| m.y() + m.height() as i32).max().unwrap_or(0);
    let total_w = (max_x - min_x) as u32;
    let total_h = (max_y - min_y) as u32;

    // 2. 创建透明画布（黑色/透明填充显示器之间的空隙区域）
    let mut canvas = RgbaImage::from_pixel(total_w, total_h, Rgba([0, 0, 0, 255]));

    // 3. 逐个显示器截取并贴到画布对应位置
    for monitor in &monitors {
        let image = monitor.capture_image()
            .map_err(|e| format!("截取显示器失败: {e}"))?;
        let offset_x = (monitor.x() - min_x) as u32;
        let offset_y = (monitor.y() - min_y) as u32;
        image::imageops::overlay(&mut canvas, &image, offset_x as i64, offset_y as i64);
    }

    let bounds = VirtualScreenBounds {
        x: min_x,
        y: min_y,
        width: total_w,
        height: total_h,
    };
    Ok((canvas, bounds))
}
```

**`capture_virtual_region()` 跨屏截取逻辑（用于录制）：**

```rust
/// 录制场景：每帧从虚拟桌面坐标截取，选区可能跨屏
/// x, y 是虚拟桌面坐标（物理像素）
pub fn capture_virtual_region(
    x: i32, y: i32, width: u32, height: u32
) -> Result<RgbaImage, String> {
    let monitors = get_all_monitors()?;

    // 优化路径：如果选区完全在一个显示器内，直接用 capture_region_from
    if let Some(monitor) = find_single_containing_monitor(&monitors, x, y, width, height) {
        let local_x = (x - monitor.x()) as u32;
        let local_y = (y - monitor.y()) as u32;
        return capture_region_from(&monitor, local_x, local_y, width, height);
    }

    // 跨屏路径：创建画布，从每个涉及的显示器截取重叠部分并拼接
    let mut canvas = RgbaImage::from_pixel(width, height, Rgba([0, 0, 0, 255]));

    let sel_rect = Rect { x, y, w: width as i32, h: height as i32 };
    for monitor in &monitors {
        let mon_rect = Rect {
            x: monitor.x(), y: monitor.y(),
            w: monitor.width() as i32, h: monitor.height() as i32,
        };
        if let Some(overlap) = sel_rect.intersect(&mon_rect) {
            // 从该显示器截取重叠区域
            let local_x = (overlap.x - monitor.x()) as u32;
            let local_y = (overlap.y - monitor.y()) as u32;
            let region = capture_region_from(
                &monitor, local_x, local_y, overlap.w as u32, overlap.h as u32
            )?;
            // 贴到画布上的对应位置
            let canvas_x = (overlap.x - x) as i64;
            let canvas_y = (overlap.y - y) as i64;
            image::imageops::overlay(&mut canvas, &region, canvas_x, canvas_y);
        }
    }

    Ok(canvas)
}

/// 判断选区是否完全落在单个显示器内（快速路径优化）
fn find_single_containing_monitor(
    monitors: &[Monitor], x: i32, y: i32, w: u32, h: u32
) -> Option<&Monitor> {
    monitors.iter().find(|m| {
        x >= m.x()
        && y >= m.y()
        && x + w as i32 <= m.x() + m.width() as i32
        && y + h as i32 <= m.y() + m.height() as i32
    })
}
```

**DPI 不一致时的处理（Windows 双屏不同 DPI）：**

Windows 的 DPI 虚拟化机制使得 `xcap` 在 Per-Monitor DPI Aware 模式下获取的截图已经是物理像素，不同显示器的物理像素天然对齐到虚拟桌面坐标系。因此拼接时**不需要额外的缩放处理**——每个显示器截出来的图像像素坐标已经与其在虚拟桌面中的物理像素位置一致。

> 注意：如果两个显示器分辨率/高度不同（如 1440p + 1080p），bounding box 中不被任何显示器覆盖的区域填充黑色（`Rgba([0, 0, 0, 255])`），这与主流截屏工具行为一致。

**保留不删：**
- `capture_primary_screen()` — 向后兼容，内部改为调用 `capture_screen(primary)`
- `capture_region()` — 向后兼容，内部改为调用 `capture_region_from(primary, ...)`

**跨屏录制的性能考量：**

| 场景 | 路径 | 性能影响 |
|------|------|----------|
| 选区在单个显示器内 | `find_single_containing_monitor` → 直接 `capture_region_from` | 无额外开销 |
| 选区跨两个显示器 | 两次 `capture_region_from` + 一次 `overlay` 拼接 | 每帧多一次截取 + 内存拷贝 |

大多数用户的录制选区不会跨屏，快速路径覆盖 99% 场景。跨屏时的额外开销在 15fps/30fps 下可接受（拼接操作是纯内存操作，微秒级）。

```typescript
        height: rect.height,
    };
    invoke("snap_region", { region });
}
```

**macOS（方案 B）：**

每个 overlay 的 Canvas 只对应自己那个显示器，尺寸 = 该显示器逻辑尺寸。选区坐标是相对于该显示器的局部坐标，传给 Rust 时需附带 monitor index。

```typescript
// macOS 下 overlay 知道自己对应哪个显示器
const monitorIndex = parseInt(params.get("monitor") || "0");

function confirmSelection(rect: Rect) {
    const region = {
        x: rect.x,
        y: rect.y,
        width: rect.width,
        height: rect.height,
        monitor_index: monitorIndex,  // 新增字段
    };
    invoke("snap_region", { region });
}
```

#### 3.2.3 通信桥新增

`bridge/shared/invoke.ts` 或各 bridge 文件中新增：

```typescript
interface MonitorInfo {
    id: string;
    x: number;
    y: number;
    width: number;
    height: number;
    scale_factor: number;
    is_primary: boolean;
}

export async function getScreenInfo(): Promise<MonitorInfo[]> {
    return invoke<MonitorInfo[]>("get_screen_info");
```

### 3.3 macOS 方案 B 的特殊处理

#### 3.3.1 多 overlay 状态同步

用户在任意 overlay 上按 Esc 或点击关闭，**所有 overlay 都要同步关闭**。实现方式：

- 前端 overlay 触发关闭时，调用 `close_overlay` 命令
- Rust 端 `hide_overlay()` 遍历关闭所有 `overlay-N` 窗口
- 已有的 `hide_overlay()` 函数改为遍历逻辑即可，无需额外事件

#### 3.3.2 焦点管理

触发截屏/录制时，需要聚焦到鼠标所在的 overlay 窗口：

```rust
fn focus_overlay_at_cursor(app: &AppHandle) -> Result<(), String> {
    // 1. 获取鼠标当前位置
    // 2. 判断鼠标在哪个显示器上
    // 3. set_focus() 对应的 overlay-N
}
```

获取鼠标位置的方式：
- 可复用已有的 `rdev` 依赖（Windows/Linux）
- macOS 用 `CGEvent::mouseLocation()` 或 Tauri 的 `cursor_position()`

#### 3.3.3 显示器数量变化

应用启动时按当前显示器数量创建 overlay 窗口。如果用户后续接入/断开显示器：
- 不做实时响应（YAGNI）
- 用户重启应用后自动适配新的显示器配置
- 可在托盘菜单的截屏/录制触发时做一次显示器数量检查，如果变了则重建 overlay（可选优化，不在首版实现）

## 四、坐标系梳理

这是最容易出错的部分，单独梳理清楚。

### 4.1 三套坐标系

```
┌─────────────────────────────────────────────────────────┐
│  虚拟桌面坐标系（物理像素）                                │
│  原点：所有显示器 bounding box 左上角                      │
│  范围：可能包含负坐标（副屏在主屏左边时）                    │
│  使用者：xcap Monitor::x()/y()、屏幕捕获坐标               │
├─────────────────────────────────────────────────────────┤
│  显示器局部坐标系（物理像素）                                │
│  原点：该显示器左上角                                      │
│  范围：(0,0) 到 (width, height)                          │
│  使用者：xcap capture_region() 的参数                     │
├─────────────────────────────────────────────────────────┤
│  Tauri/WebView 逻辑坐标系（逻辑像素）                      │
│  原点：窗口左上角                                         │
│  换算：逻辑像素 = 物理像素 / scale_factor                  │
│  使用者：前端 Canvas 坐标、窗口 position/size              │
└─────────────────────────────────────────────────────────┘
```

### 4.2 坐标转换流程

**截屏（snap）：**

```
前端选区(逻辑坐标, 相对于 overlay 窗口)
  ↓ + overlay 窗口在虚拟桌面中的偏移
虚拟桌面逻辑坐标
  ↓ × scale_factor（选区所在显示器的）
虚拟桌面物理坐标
  ↓ - monitor.x()/y()（选区所在显示器的偏移）
显示器局部物理坐标
  ↓ 传给 xcap capture_region_from()
截取结果
```

**录制（GIF/Video）同上流程，每帧重复 capture 步骤。**

### 4.3 Windows 负坐标示例

```
显示器布局（物理像素）：

副屏 (1920x1080)          主屏 (2560x1440)
┌──────────────┐    ┌──────────────────┐
│              │    │                  │
│ x=-1920,y=0  │    │  x=0, y=0       │
│              │    │                  │
└──────────────┘    └──────────────────┘

虚拟桌面 bounding box：
  x = -1920, y = 0
  width = 1920 + 2560 = 4480
  height = 1440（取最大）

overlay 窗口：
  position = (-1920, 0) → 逻辑坐标需除以 scale
  size = (4480, 1440) → 逻辑坐标需除以 scale
```

## 五、数据流图

### 5.1 截屏流程（改造后）

```
用户按 F1
  ↓
Rust: open_snap_overlay()
  ├─ [Win/Linux] capture_virtual_screen()
  │    └─ 枚举所有显示器 → 逐个截取 → 拼接为虚拟桌面大图
  │    └─ 存入 ScreenBuffer { image: 拼接大图, bounds: bounding_box }
  ├─ [macOS] capture_screen(鼠标所在显示器)
  │    └─ 存入 ScreenBuffer { image: 单屏截图, bounds: 该显示器区域 }
  ├─ show_overlay()
  │    ├─ [Win/Linux] 单 overlay 覆盖虚拟桌面 bounding box
  │    └─ [macOS] 显示所有 overlay-N，聚焦鼠标所在的
  └─ emit("overlay-mode", "snap-overlay")
       ↓
前端: SelectionOverlay 初始化
  ├─ invoke("get_screen_info") 获取显示器布局
  ├─ [Win/Linux] Canvas 尺寸 = 虚拟桌面大小，用户可跨屏拖拽选区
  ├─ [macOS] Canvas 尺寸 = 当前显示器大小
  └─ 用户拖拽选区（可跨屏）→ 确认
       ↓
Rust: snap_region(region)
  ├─ 逻辑坐标 × scale → 物理坐标
  ├─ 从 ScreenBuffer 的虚拟桌面大图中 crop（跨屏区域自然包含）
  ├─ 保存文件 + 复制到剪贴板
  └─ hide_overlay()
```

### 5.2 录制流程（改造后）

```
用户按 F3/F5 → overlay 选区（可跨屏）→ 确认
  ↓
Rust: gif_start() / video_start()
  ├─ 逻辑坐标 × scale → 虚拟桌面物理坐标
  ├─ 启动录制线程
  │    └─ 每帧: capture_virtual_region(x, y, w, h)
  │         ├─ 快速路径：选区在单个显示器内 → capture_region_from()
  │         └─ 跨屏路径：从涉及的每个显示器截取重叠部分 → 拼接
  ├─ hide_overlay()
  └─ 创建浮动窗口（record-bar, record-region, record-info）
       └─ 浮动窗口用逻辑坐标定位，Tauri 自动放到正确显示器上
```

## 六、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| Windows 负坐标导致窗口定位错误 | overlay 不能完全覆盖副屏 | 单元测试覆盖负坐标场景；手动测试双屏（副屏在左/上） |
| 虚拟桌面预截拼接内存占用大 | 双 4K 显示器拼接 ~60MB RGBA | 可接受，截屏完成后立即释放；录制不走预截，每帧只截选区 |
| 跨屏录制帧率下降 | 每帧两次截取 + 拼接 | 快速路径优化：99% 场景选区在单屏内，不走拼接；跨屏时拼接是纯内存操作，开销可控 |
| 跨屏区域不同 DPI（Windows 100%+125%） | 拼接图像像素密度不一致 | Windows DPI 虚拟化已在物理像素层面统一；实测验证后再决定是否需要缩放 |
| 显示器之间有空隙（高度不同） | 截图包含黑色填充区域 | 与主流工具行为一致（填充黑色），可接受 |
| macOS 多 overlay 间事件不同步 | 用户按 Esc 只关了一个 overlay | `hide_overlay()` 遍历关闭所有；前端也通过 Rust 命令关闭而非本地处理 |
| xcap 与 Tauri 坐标系不一致 | 截取区域偏移 | 启动时打印所有 Monitor 坐标日志做比对验证 |
| macOS 显示器排列非标准（竖向、旋转） | 坐标计算错误 | 首版只测试标准横向排列；后续根据用户反馈补充 |
| 录制过程中显示器 DPI 变化（系统偏好设置） | 帧尺寸突变导致编码失败 | 录制启动时锁定 monitor 和 scale，整个录制过程不再重新获取 |
