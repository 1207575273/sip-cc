# 录制信息叠加层（Record Info Overlay）技术方案

## 1. 问题定义

录制视频/GIF 时，用户希望在画面的右上角显示一个小型半透明面板，实时展示录制参数和状态：

- 质量档位（流畅/标准/高清）
- 分辨率 & 帧率
- 录制时长（动态计时）
- 录制状态指示（REC 闪烁圆点）

该信息需要**被录进最终的视频/GIF 文件**中，作为画面内容的一部分。

## 2. 方案对比与选型

### 方案 A：Rust 帧内像素绘制（已验证，已废弃）

之前实现过的思路：在 `session.rs` 的帧捕获循环中，每帧用 `image` crate 在 `RgbaImage` 上绘制文字。

```
capture_region() → RgbaImage → draw_overlay() → save()
                                ↑ 5x7 bitmap font
                                ↑ 逐像素 alpha blend
                                ↑ 手动排版
```

**优点**：
- 帧级精确，每帧都有
- 不依赖窗口系统

**缺点**（致命）：
- 需要嵌入位图字体，5x7 分辨率粗糙
- 手写像素绘制、alpha blending、自动缩放逻辑，代码量大（~200行）
- 无法使用 CSS 样式、圆角、阴影、渐变、动画
- 增加每帧处理耗时（尤其高分辨率下）
- 完全浪费了 Rust + WebView 的架构优势
- 难以维护和扩展（加个图标？加个动画？改个字体？全部重写）

**结论：用 Rust 做 UI 渲染是杀鸡用牛刀的反面——用牛做鸡的活。**

### 方案 B：FFmpeg drawtext 滤镜（未实施，已放弃）

在编码阶段通过 FFmpeg 的 `drawtext` 滤镜叠加文字。

**缺点**：
- 依赖系统字体路径，跨平台复杂
- Windows 字体路径包含空格和中文，转义噩梦
- 只能叠加静态文本（时间戳需要复杂表达式）
- 不影响 GIF（GIF 不走 FFmpeg）
- 无法预览——录制时看不到效果

**结论：不通用、不直观、维护成本高。**

### 方案 C：WebView 浮窗叠加（本方案 ✅）

创建一个小型透明 WebView 窗口，定位在录制区域右上角内侧。xcap 截屏时会自然捕获到这个窗口，因此信息自动出现在录制画面中。

```
┌─────────────────────────────────┐
│ 录制区域                    ┌──────────┐
│                             │ 高清 30fps│  ← record-info 窗口
│                             │ 1920×1080│     (WebView)
│                             │ 00:03:21 │
│                             └──────────┘
│                                         │
│                                         │
└─────────────────────────────────────────┘
         ┌─────────────────────┐
         │ ● 录制中  00:03  ▌▌ ■ │  ← record-bar 窗口
         └─────────────────────┘
```

**优点**：
- **架构契合**：Rust 管核心（截屏、编码、状态），WebView 管展示，各司其职
- **复用现有模式**：与 `record-bar`、`record-region` 完全同构——同样的创建时机、同样的生命周期、同样的关闭逻辑
- **CSS 全能力**：圆角、半透明背景、阴影、字体、动画（REC 圆点闪烁）、响应式布局
- **动态更新**：JS `setInterval` 实现实时计时，无需 Rust 参与
- **零帧处理开销**：不在帧捕获路径上做任何额外操作
- **天然被捕获**：xcap 截屏捕获屏幕上所有可见内容，WebView 窗口自然入画
- **GIF/Video 通用**：GIF 和 Video 的帧捕获都基于 xcap，方案完全通用
- **易于扩展**：想加 logo？加个 `<img>`。想加水印？改个 CSS。想换位置？改坐标。

**缺点**：
- 窗口创建有延迟（~100-200ms），录制最初几帧可能没有 overlay（可接受）
- 增加一个浮窗，多占少量系统资源（忽略不计）

**结论：完美契合 Tauri 架构，开发成本最低，效果最好。**

## 3. 架构设计

### 3.1 整体架构（录制期间的窗口关系）

```
                   ┌──────────────────┐
                   │   Tauri 主进程    │
                   │  (Rust backend)  │
                   └────────┬─────────┘
                            │ 管理窗口生命周期
              ┌─────────────┼─────────────┐
              │             │             │
    ┌─────────▼──┐  ┌───────▼─────┐  ┌───▼──────────┐
    │ record-bar │  │record-region│  │ record-info  │
    │  控制条     │  │  红色边框    │  │ 信息叠加层   │
    │ (区域外下方) │  │ (区域边缘)   │  │ (区域内右上)  │
    └────────────┘  └─────────────┘  └──────────────┘
         交互窗口       穿透窗口          穿透窗口

              ↓ xcap 截屏范围 ↓
    ┌─────────────────────────────────┐
    │  record-region + record-info    │  ← 这两个在截屏区域内
    │  都会被 xcap 捕获到帧画面中       │
    └─────────────────────────────────┘
    │  record-bar 在区域外，不被捕获    │
```

### 3.2 窗口属性

| 属性 | record-bar | record-region | **record-info**（新增） |
|------|-----------|--------------|----------------------|
| 位置 | 区域外下方 | 覆盖录制区域 | 区域内右上角 |
| 尺寸 | 300×44 | 与选区等大 | ~160×70 |
| transparent | ✅ | ✅ | ✅ |
| decorations | ❌ | ❌ | ❌ |
| always_on_top | ✅ | ✅ | ✅ |
| ignore_cursor_events | ❌（需交互） | ✅ | ✅ |
| 被 xcap 捕获 | ❌（区域外） | ✅ | ✅ |

### 3.3 数据流

```
video_start(region, quality)
    │
    ├─ Rust: 计算物理坐标、创建 session
    │
    └─ spawn thread:
         ├─ 创建 record-bar（区域外，不被录制）
         ├─ 创建 record-region（红色边框，被录制）
         └─ 创建 record-info（信息面板，被录制）
              │
              URL params: ?view=record-info
                          &w=1920&h=1080
                          &fps=30&quality=高清
              │
              └─ JS 端：
                   ├─ 渲染静态信息（分辨率、帧率、质量）
                   └─ setInterval 更新录制时长
```

### 3.4 生命周期

| 事件 | record-info 行为 |
|------|-----------------|
| `video_start` | 在 spawn thread 中创建，与 record-bar/record-region 同时 |
| 录制进行中 | JS 自行计时更新，无需 Rust 交互 |
| `video_pause` | 监听 Tauri event 暂停计时器（可选，不做也行） |
| `video_resume` | 恢复计时器（可选） |
| `video_stop` | 由 `close_floating_windows` 统一关闭 |

## 4. 技术细节

### 4.1 窗口定位（Rust 端）

```
info_x = log_x + log_w - INFO_WIDTH - INFO_MARGIN
info_y = log_y + INFO_MARGIN
```

- `INFO_WIDTH = 160.0`（逻辑像素）
- `INFO_HEIGHT = 70.0`
- `INFO_MARGIN = 8.0`（距离区域边缘的内边距）

### 4.2 URL 参数

```
index.html?view=record-info&w={log_w}&h={log_h}&fps={fps}&quality={quality_label}
```

| 参数 | 来源 | 用途 |
|------|------|------|
| w, h | 逻辑选区尺寸 | 显示分辨率 |
| fps | ActiveRecording.fps | 显示帧率 |
| quality | 前端传入的预设名 | 显示质量档位 |

### 4.3 前端 UI（HTML/CSS）

视觉设计：半透明深色圆角卡片，白色文字，紧凑排列。

```
┌─────────────┐
│ ● REC  高清  │  ← 闪烁红点 + 质量档位
│ 1920×1080   │  ← 分辨率
│ 30fps       │  ← 帧率
│ 00:03:21    │  ← 动态计时
└─────────────┘
```

样式要点：
- `background: rgba(0, 0, 0, 0.55)` — 半透明黑底
- `border-radius: 6px` — 圆角
- `font-family: monospace` — 等宽字体，数字不跳动
- `font-size: 11px` — 紧凑
- `padding: 8px 12px`
- REC 圆点用 CSS `@keyframes` 做闪烁动画

## 5. 改动范围评估

| 文件 | 改动类型 | 工作量 |
|------|---------|--------|
| `ui/views/RecordInfo.ts` | **新建** | 核心文件，~50行 |
| `ui/styles/overlay.css` | 追加样式 | ~30行 CSS |
| `ui/main.ts` | 加路由 | 2行 |
| `src-tauri/src/commands/video_cmd.rs` | 创建窗口 | ~15行 |
| `src-tauri/src/commands/gif_cmd.rs` | 同上（GIF 复用） | ~15行 |
| `src-tauri/src/commands/snap_cmd.rs` | close list 加 `"record-info"` | 1行 |

**总计：~6 个文件，~110 行代码，0 个新依赖。**

与方案 A 的对比：方案 A 需要 `overlay.rs`（~200行）+ `session.rs` 大改 + `encoder.rs` 大改 + bitmap 字体数据（~500行），约 4 个文件 700+ 行。

## 6. 风险与边界

| 风险 | 严重性 | 应对 |
|------|-------|------|
| 窗口创建延迟导致前几帧无 overlay | 低 | 录制前 150ms 已预留窗口创建时间（OVERLAY_SETTLE_DELAY），实际影响 < 5 帧 |
| 极小选区（< 200px 宽）时 overlay 溢出 | 低 | 当 `log_w < INFO_WIDTH + INFO_MARGIN * 2` 时不创建 info 窗口 |
| 多显示器 DPI 不一致 | 低 | 与现有 record-region 同级别问题，非本方案引入 |
| GIF 帧率低时计时器不精确 | 无 | 计时器在 JS 端独立运行，与帧捕获频率无关 |

## 7. 结论

**方案 C（WebView 浮窗叠加）是最优解**。

它不是"用最简单的方式解决问题"，而是"用最契合架构的方式解决问题"：

- Rust 只管底层：截屏、编码、状态、窗口生命周期
- WebView 管一切展示：布局、样式、动画、动态更新
- xcap 天然桥接：WebView 窗口出现在屏幕上 → 截屏自然录进去

**不需要在 Rust 层面做任何图像处理，不需要位图字体，不需要像素操作。** 整个方案的 Rust 改动只有"多创建一个窗口 + 多关闭一个窗口"。

这才是 Tauri 架构该有的样子。
