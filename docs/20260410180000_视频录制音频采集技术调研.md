# 视频录制 — 音频采集技术调研

> 调研时间：2026-04-10
> 状态：待决策

## 1. 需求场景

| 场景 | 音频来源 | 典型用途 | 优先级评估 |
|---|---|---|---|
| 教程/演示录屏 | 麦克风（人声讲解） | 录操作教程配旁白 | 高 |
| 软件问题反馈 | 系统声音（桌面音频） | 复现带声音的 bug | 中 |
| 会议/直播录制 | 系统 + 麦克风混合 | 录远程会议/直播 | 低（竞品覆盖） |

## 2. 现有架构回顾

```
当前录制流程（纯视频，无音频）：

  xcap 截屏 → BMP 帧序列 (session.rs)
                   ↓ 停止录制后
              FFmpeg 编码 (encoder.rs)
                   ↓
              H.264 MP4 输出
```

关键约束：
- 录制期间 FFmpeg **不参与**（二阶段设计：先帧采集、后编码）
- 视频帧按固定间隔采集（sleep 补偿），**没有精确时间戳**
- 暂停/继续通过 AtomicU8 状态标志控制

## 3. 各平台音频采集技术调研

### 3.1 Rust 生态主力：cpal

`cpal` — Rust 社区最主流的跨平台音频 I/O 库（crates.io 累计 870 万+ 下载）。

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 麦克风采集 | WASAPI ✅ | CoreAudio ✅ | ALSA ✅ |
| 系统声音（Loopback） | WASAPI Loopback ✅ (自 2020) | CoreAudio ProcessTap ✅ (自 2025.09, 需 macOS 14.2+) | PipeWire ⚠️ (仅 master 分支, 未发布到 crates.io) |
| 最新版本 | 0.17.x | 0.17.x | 0.17.x |

**Windows 系统声音采集方式**：
```rust
// 在 output device 上创建 input stream → WASAPI 自动启用 Loopback
let output_device = host.default_output_device().unwrap();
let config = output_device.default_output_config().unwrap();
let stream = output_device.build_input_stream(&config, data_callback, err_callback, None);
```
原理：WASAPI 检测到在输出设备上建 input stream，自动设置 `AUDCLNT_STREAMFLAGS_LOOPBACK` 标志。

**macOS 系统声音采集方式**：
- cpal 0.17+ 使用 `AudioHardwareCreateProcessTap`（macOS 14.2+）
- 需要应用有 "Screen Recording" 权限
- 旧系统（< 14.2）不支持，需第三方虚拟音频驱动（BlackHole、Soundflower）

**Linux 系统声音**：
- PipeWire 后端尚未发布到 crates.io
- ALSA 不原生支持 loopback，需 PulseAudio monitor 设备
- 如果只用麦克风，ALSA 后端即可

### 3.2 替代方案：FFmpeg 直接采集

FFmpeg 本身有音频采集能力（通过 `-f` 指定输入格式）：

| 平台 | 命令 | 说明 |
|---|---|---|
| Windows | `-f dshow -i audio="Stereo Mix"` | 需声卡支持 Stereo Mix（很多笔记本默认禁用） |
| macOS | 不支持 | 无原生 loopback，需虚拟驱动 |
| Linux | `-f pulse -i default` | 通过 PulseAudio/PipeWire |

### 3.3 macOS 专有：ScreenCaptureKit

Apple 原生框架，macOS 12.3+ 支持同时采集屏幕画面 + 系统音频 + 麦克风（macOS 15+）。

- 优势：一个 API 同时拿视频帧和音频，天然同步
- 劣势：仅限 macOS，需要 Swift/ObjC 桥接到 Rust，与现有 `xcap` 架构完全不同
- 评估：**不适合当前跨平台项目**，除非未来做 macOS 专属优化

## 4. 技术方案对比

### 方案 A：cpal 采集 PCM → WAV → FFmpeg 合并（推荐）

```
录制阶段（并行双线程）：
  线程1: xcap 截屏 → BMP 帧序列
  线程2: cpal 采集 → PCM 数据 → 写入 WAV 文件

编码阶段：
  FFmpeg -i frame_%06d.bmp -i audio.wav → MP4 (H.264 + AAC)
```

**FFmpeg 合并命令**：
```bash
ffmpeg -framerate 15 -start_number 1 -i frame_%06d.bmp \
       -i audio.wav \
       -c:v libx264 -crf 23 -preset veryfast \
       -c:a aac -b:a 128k \
       -pix_fmt yuv420p -movflags +faststart \
       -map 0:v:0 -map 1:a:0 \
       output.mp4
```

**音视频同步方案**：
- 视频帧按 `1/fps` 固定间隔（CFR），FFmpeg 用 `-framerate` 精确指定
- 音频 WAV 从录制开始时间同步开启/暂停/停止
- 暂停期间：视频停止截帧，音频停止写入（使用同一个 AtomicU8 状态标志）
- FFmpeg 编码时 `-shortest` 对齐较短的流，或用 `-af atrim` 裁剪

**改动范围**：

| 文件 | 改动 |
|---|---|
| `Cargo.toml` | +`cpal = "0.17"`, +`hound = "3"` (WAV 读写) |
| `video/audio.rs` (新) | AudioRecordingSession：cpal 采集 + WAV 写入 |
| `video/session.rs` | 新增 `audio_path` 字段，start 时同时启动音频线程 |
| `video/encoder.rs` | FFmpeg 命令增加 `-i audio.wav -c:a aac` 参数 |
| `config.rs` | 新增 `audio_source: String` 配置（none/mic/system/both） |
| `video_cmd.rs` | 传递音频配置到 session |
| 前端 | 录制前添加音频源选择 UI（可选） |

**优势**：
- 与现有二阶段架构完美兼容
- cpal 纯 Rust，无外部依赖
- 麦克风采集三平台通用，无兼容问题
- WAV 是无压缩格式，写入零延迟

**劣势**：
- WAV 临时文件较大（30s 录音 ≈ 5MB @ 44.1kHz 16bit 双声道）
- 系统声音采集在 macOS < 14.2 和部分 Linux 上不可用
- 暂停/继续的音频同步需要仔细处理

**开发成本**：3~5 天

---

### 方案 B：FFmpeg 全程运行（录制期间同时编码）

```
录制阶段：
  FFmpeg 进程启动 (stdin pipe)
  循环: xcap 截屏 → raw RGBA → pipe 到 FFmpeg stdin
  同时: FFmpeg 自己采集音频输入设备

编码：实时完成，停止录制时 FFmpeg 关闭即产出 MP4
```

**优势**：
- 音视频同步由 FFmpeg 内部处理，最准确
- 无临时帧文件，省磁盘 I/O
- 停止即完成，无编码等待

**劣势**：
- **架构大改**：完全推翻当前二阶段设计
- FFmpeg 必须在录制开始前就可用（当前是按需下载）
- 暂停/继续需要精确控制 pipe 流，容易产生音画不同步
- 录制期间 FFmpeg 进程持续占用 CPU（编码+采集同时进行）
- FFmpeg 音频采集在 macOS 上不可用
- 异常处理复杂：FFmpeg 进程崩溃 = 丢失全部数据

**开发成本**：7~10 天（含架构重构）

---

### 方案 C：仅麦克风、最小方案

只支持麦克风，不支持系统声音。

```
与方案 A 相同架构，但只用 cpal 的 default_input_device（麦克风）
```

**优势**：
- 三平台完全统一，无兼容问题
- cpal 麦克风采集是最成熟的路径
- 代码量最小

**劣势**：
- 不能录系统声音

**开发成本**：2~3 天

## 5. 综合对比

| 维度 | 方案 A (cpal+WAV) | 方案 B (FFmpeg 全程) | 方案 C (仅麦克风) |
|---|---|---|---|
| 架构变动 | 小（增量） | 大（重构） | 最小 |
| 麦克风 | ✅ 全平台 | ✅ Win/Linux, ❌ Mac | ✅ 全平台 |
| 系统声音 | ✅ Win, ⚠️ Mac(14.2+), ⚠️ Linux | ⚠️ Win, ❌ Mac, ⚠️ Linux | ❌ |
| 音视频同步 | 良好（CFR + WAV 对齐） | 最好（FFmpeg 内部） | 良好 |
| 暂停/继续 | 中等复杂度 | 高复杂度 | 中等复杂度 |
| 开发成本 | 3~5 天 | 7~10 天 | 2~3 天 |
| 风险 | 低 | 高（架构翻新） | 最低 |
| 包体增量 | cpal ~200KB | 无 | cpal ~200KB |

## 6. 风险评估

### 6.1 音视频同步风险

当前视频帧采集用 `thread::sleep` 补偿帧间隔，没有精确时间戳。在以下情况可能出现音画不同步：

- **帧采集卡顿**：某帧截屏耗时超过帧间隔 → 实际帧率 < 设定帧率 → 视频变慢、音频正常 → 音画漂移
- **暂停/继续**：如果音视频暂停时刻不精确同步，会产生偏移

**缓解措施**：
- 记录每帧的实际时间戳，编码时用 VFR（可变帧率）
- 或者：音频侧也按同样逻辑暂停（共享同一个 AtomicU8），暂停期间不写入 PCM → WAV 和 BMP 帧序列天然对齐

### 6.2 macOS 权限风险

- 系统声音采集需要 "Screen Recording" 权限弹窗
- macOS < 14.2 不支持原生 loopback → 需告知用户不可用
- App Store 审核可能对音频采集权限有额外要求

### 6.3 Linux 兼容性风险

- cpal 的 PipeWire 后端未发布到 crates.io
- 仅 ALSA 后端可用，不支持系统声音 loopback
- 麦克风可用

## 7. 建议

**推荐路径：方案 C（仅麦克风）先行 → 后续迭代升级为方案 A**

理由：
1. **麦克风是最高频需求**（教程/演示场景），系统声音是次要需求
2. **方案 C 零兼容风险**，三平台统一，不需要条件编译
3. **方案 C 改动量最小**（2~3 天），与现有架构无冲突
4. 后续如果需要系统声音，从 C 升级到 A 只需：
   - 改 `cpal` 的设备选择逻辑（`default_input_device` → `default_output_device` for loopback）
   - 加平台条件编译
   - 前端加音频源选择

**如果决定做，一期交付物**：
- 配置项 `audio_enabled: bool`（默认 false）
- 录制时如果 audio_enabled = true，同时启动麦克风采集
- 编码阶段 FFmpeg 自动合并音轨
- RecordBar 增加麦克风开关图标
