# macOS 截屏遮罩尺寸异常修复方案

## 1. 问题现象

macOS 用户反馈：按快捷键截屏时，**只弹出一个小的黑色遮罩**（约为屏幕 1/4 大小），只能在该小区域内框选截屏，无法覆盖全屏。

## 2. 根因分析

### 2.1 直接原因：逻辑/物理像素换算错误

`snap_cmd.rs` 中 `get_screen_logical_size()` 的计算逻辑：

```rust
fn get_screen_logical_size() -> (f64, f64) {
    let scale = get_scale_factor();       // xcap: Monitor::scale_factor()
    Monitor::all()
        .ok()
        .and_then(|monitors| monitors.into_iter().find(|m| m.is_primary().unwrap_or(false)))
        .map(|m| {
            let w = m.width().unwrap_or(1920) as f64 / scale;   // ← BUG
            let h = m.height().unwrap_or(1080) as f64 / scale;  // ← BUG
            (w, h)
        })
        .unwrap_or((1920.0, 1080.0))
}
```

**这段代码假设 `xcap::Monitor::width()` 返回物理像素，然后除以 scale 得到逻辑像素。但在 macOS 上，xcap 底层调用 `CGDisplayPixelsWide()` 等 CoreGraphics API，返回值取决于 macOS 版本和显示模式，可能已经是逻辑尺寸（points）。**

以 MacBook Pro 14" (M1 Pro, Retina) 为例：

| 维度 | 物理像素 | 逻辑点 | scale_factor |
|------|---------|--------|-------------|
| 宽 | 3024 | 1512 | 2.0 |
| 高 | 1964 | 982 | 2.0 |

**如果 `width()` 返回逻辑值 1512**：
```
w = 1512 / 2.0 = 756   ← 只有屏幕宽度的一半
h = 982 / 2.0  = 491   ← 只有屏幕高度的一半
```

overlay 窗口被设为 756×491 → 用户看到的"小黑遮罩"。

### 2.2 叠加因素

| 问题 | 位置 | 影响 |
|------|------|------|
| overlay 窗口初始化无尺寸 | `lib.rs` 第 70-83 行 | macOS 上创建时不设 fullscreen 也不设 size，默认为 Tauri 默认尺寸（~800×600） |
| `set_size` 错误被吞掉 | `snap_cmd.rs` 第 61 行 | `let _ = win.set_size(...)` 失败无日志 |
| `is_primary()` 不可靠 | `snap_cmd.rs` 第 40 行 | xcap 在某些 macOS 配置下无法识别主显示器 |
| 缺少 Screen Recording 权限 | 系统层 | xcap 获取显示器信息可能需要此权限，无权限时可能返回错误数据 |

### 2.3 问题链

```
xcap::Monitor::width() 在 macOS 可能返回逻辑点(1512)
            ↓
get_screen_logical_size() 再除以 scale(2.0) = 756
            ↓
set_size(756, 491) → overlay 只有屏幕 ~1/4
            ↓
用户看到 "小的黑遮罩"
```

### 2.4 为什么 Windows 上不出问题

Windows 上走的是 `set_fullscreen(true)` 分支（`lib.rs` 第 80 行），完全不依赖 `get_screen_logical_size()`。只有 macOS 因为"fullscreen 会创建独立 Space 导致黑屏"而走手动设置尺寸的逻辑。

## 3. 修复方案

### 方案选型

| 方案 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| A. 用 Tauri 的 Monitor API | `app.primary_monitor()` → `PhysicalSize` / `scale_factor` | Tauri 内部已处理平台差异，API 语义明确（PhysicalSize = 物理像素） | 需要在 `show_overlay` 中传入 `AppHandle` |
| B. 用 NSScreen API (macOS only) | `#[cfg(target_os = "macos")]` 调用 NSScreen.frame | 最精确，直接拿 macOS 窗口系统的逻辑尺寸 | 平台特定代码，增加维护成本 |
| C. 不除以 scale，直接用 xcap 返回值 | 去掉 `/ scale` | 最简单 | 不确定 xcap 跨平台行为是否一致 |

**推荐方案 A**：使用 Tauri 自带的 `primary_monitor()` API。

理由：
- Tauri 的 Monitor API 底层使用 `tao`（跨平台窗口库），在 macOS 上通过 `NSScreen` 获取数据，语义明确
- `Monitor::size()` 明确返回 `PhysicalSize<u32>`（物理像素），`scale_factor()` 返回 DPI 缩放
- 逻辑尺寸 = `PhysicalSize / scale_factor`，计算无歧义
- 不引入新依赖，复用 Tauri 已有能力
- 已在 Tauri v2 中稳定可用

### 修复实施

#### 3.1 改造 `get_screen_logical_size()`

**改前**（依赖 xcap）：
```rust
fn get_screen_logical_size() -> (f64, f64) {
    let scale = get_scale_factor();
    Monitor::all()
        .ok()
        .and_then(|monitors| monitors.into_iter().find(|m| m.is_primary().unwrap_or(false)))
        .map(|m| {
            let w = m.width().unwrap_or(1920) as f64 / scale;
            let h = m.height().unwrap_or(1080) as f64 / scale;
            (w, h)
        })
        .unwrap_or((1920.0, 1080.0))
}
```

**改后**（使用 Tauri Monitor API）：
```rust
fn get_screen_logical_size(app: &AppHandle) -> (f64, f64) {
    app.primary_monitor()
        .ok()
        .flatten()
        .map(|m| {
            let phys = m.size();
            let scale = m.scale_factor();
            (phys.width as f64 / scale, phys.height as f64 / scale)
        })
        .unwrap_or((1920.0, 1080.0))
}
```

语义清晰：
- `m.size()` → `PhysicalSize { width: 3024, height: 1964 }` （物理像素，Tauri 文档明确）
- `m.scale_factor()` → `2.0`
- 逻辑尺寸 = `3024/2.0 = 1512`, `1964/2.0 = 982` ✅

#### 3.2 同步改造 `get_scale_factor()`

当前也依赖 xcap，统一改为 Tauri API：

```rust
pub fn get_scale_factor(app: &AppHandle) -> f64 {
    app.primary_monitor()
        .ok()
        .flatten()
        .map(|m| m.scale_factor())
        .unwrap_or(1.0)
}
```

#### 3.3 调用方适配

`get_scale_factor()` 和 `get_screen_logical_size()` 新增 `app: &AppHandle` 参数，所有调用方需要传入 `app`：

| 调用位置 | 改动 |
|---------|------|
| `snap_cmd.rs` → `show_overlay()` | 已有 `app` 参数 |
| `snap_cmd.rs` → `snap_region()` | 已有 `app: AppHandle` |
| `video_cmd.rs` → `video_start()` | 已有 `app: AppHandle` |
| `gif_cmd.rs` → `gif_start()` | 已有 `app: AppHandle` |

所有调用方本身都有 `app`/`AppHandle`，传参成本为零。

#### 3.4 增加日志

在 `show_overlay` 中增加日志输出实际计算值，便于远程排查：

```rust
if cfg!(target_os = "macos") {
    let (w, h) = get_screen_logical_size(&app);
    eprintln!("[OVERLAY] macOS screen logical size: {}x{}", w, h);
    // ...
}
```

## 5. 验证方式

### 本地验证（如有 macOS 设备）

1. 启动应用，按 F1 触发截屏
2. 观察 overlay 遮罩是否覆盖全屏
3. 检查日志输出的 `screen logical size` 是否与系统"显示器"设置中的分辨率一致
4. 在"系统设置 → 显示器 → 缩放分辨率"切换不同选项后重复测试

### 远程验证（让用户测试）

1. 让 macOS 用户运行新版本
2. 收集日志中 `[OVERLAY] macOS screen logical size` 的值
3. 让用户提供"系统设置 → 显示器"的截图，对比逻辑分辨率是否匹配

## 6. 风险评估

| 风险 | 级别 | 说明 |
|------|------|------|
| Tauri `primary_monitor()` 返回 None | 低 | 有 `unwrap_or((1920, 1080))` fallback，与现状一致 |
| 多显示器场景 | 低 | `primary_monitor()` 只取主显示器，与现有逻辑一致 |
| Windows/Linux 行为变化 | 无 | Windows 走 fullscreen 分支不受影响；Linux 同理；`get_scale_factor` 改用 Tauri API 在所有平台上更一致 |
