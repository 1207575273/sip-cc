# 长截图（滚动截图）技术沉淀

> 日期：2026-04-11 | 状态：需求与方案沉淀（未绑定具体实现）  
> 读者：产品、架构、工程、算法相关同学均可阅读；尽量少公式，多用比喻与条目说明。  
> 另含 **前端遮罩**（§2.6）、**入口与保存区**（§1.6、§2.7）：交互与采集原理分开写清。

---

## 0. 先用一句话说清楚

**长截图**就是：对着同一块「能上下滚动的内容」，**多截几张屏**，再**像拼长图一样竖着接起来**，得到一张超过一屏高度的图片。

它和「截当前屏幕一块矩形」用的是同一类**截屏能力**；多出来的是三件事：**怎么自动滚**、**多张图怎么对齐**、**怎么拼成一张**。本文从**架构、工程、算法**三个角度把这件事讲透，并单独说明**遮罩层上能做哪些交互与可视化**（不改变「像素从哪来」），方便后续立项或做 Spike。

---

## 1. 架构师视角：边界、模块与风险

### 1.1 要解决的用户问题

- 用户在看**很长的网页、聊天记录、文档、代码**时，希望**一张图**带走全部内容，而不是截很多张再手工拼。

### 1.2 能力边界（建议写进产品说明）

| 适合尽力支持 | 难以保证「完美一张图」 |
|--------------|-------------------------|
| 内容大致静态、滚动后只是整体上移 | 直播、视频区域、强动画 |
| 传统列表/文档式滚动 | **虚拟列表**（只渲染可见行，滚过去内容会变） |
| 浏览器、记事本、多数办公软件 | 全屏游戏、受 DRM 保护的画面 |
| **纵向**长图（上下滚） | 同时要横纵双向（复杂度高一个量级） |

**结论**：架构上应把长截图定位为**增强能力**，带**明确的不保证清单**与**硬上限**（最大高度、最大张数、超时），避免拖垮机器或引发「怎么和宣传不一致」的客诉。

### 1.3 与现有产品的关系（概念模块）

在已有「区域截屏 / 多显示器」之上，可抽象为三层：

1. **采集层**：照旧——按矩形从屏幕（或窗口客户区）取像素。  
2. **调度层（新增）**：负责**把目标窗口置于合适状态**、**发送滚轮/翻页**、**决定何时停**。  
3. **合成层（新增）**：把多帧**对齐**、**裁切重叠**、**拼成一张大图**并导出。

这样**截屏管线不必推倒重来**，长截图是**调度 + 合成**两条新能力挂在旁边。

若在前端增加**长截图专用遮罩**（见 §2.6），架构上可再抽象一层轻量的 **呈现与交互层**：取景框、进度胶片、预览条、取消——**不负责**产生像素，只负责**让用户「看见过程」和「少迷路」**。

### 1.4 风险与合规（架构上要占位）

- **隐私**：连续截屏包含更多信息，保存路径与权限提示应与现有策略一致。  
- **性能与内存**：输出图高度 × 宽度 × 通道数可能很大，需**像素或张数上限**。  
- **平台差异**：Windows / macOS / Linux 在「焦点、滚轮注入、权限」上不一致，**不要假设一套 API 打天下**。

### 1.5 演进策略（建议）

- **第一期**：纵向、单平台或少量场景验证闭环（见工程视角）。  
- **第二期**：补齐多平台、优化失败提示与可取消体验。  
- **可选专线**：仅针对 Chrome/Edge 等，用浏览器专用能力做「整页截图」，与「通用滚动拼接」**分两条产品线**，避免互相拖累。

### 1.6 能力归属与入口：挂在「截屏」上，保存/退出区进长截图

**能力归属**

- 长截图视为 **截屏（Snap）能力的增强模式**，与 GIF 录制、视频录制等**并列层级上仍从属于「截图/截屏」产品域**（而非单独做一个与截屏无关的一级功能）。  
- 启用方式：仅在用户**已进入截屏流程**（例如已框选区域、遮罩已展示）的前提下，才提供「升级为长截图」的路径——避免用户从托盘/菜单里误以为可以不截屏直接长截。

**入口位置（建议）**

- 在截屏流程末段、用户即将**保存当前帧并退出**的界面（即现有 **保存、取消/退出** 所在区域——底部工具栏、侧边操作条或确认条均可，以你们现网布局为准），**增加一个「长截图」操作**：  
  - 表现形式：**独立按钮**，或 **图标按钮**（需配 **tooltip / 副文案**，如「长截图（滚动拼接）」）。  
  - 与「保存并退出」相邻，便于发现，但**视觉权重**上略低于主保存按钮，降低误触（长截图耗时长、可能失败）。

**点击后的预期**

- 以**当前选区/取景范围**作为长截图的固定矩形（与 §2.1、§2.6 一致），进入**长截图会话**（调度 + 多帧采集 + 合成）；**不再**仅输出单帧，除非用户中途取消并回到「仅保存当前帧」的选择。  
- 若实现上分两步：也可先 **二次确认**（「将对当前区域进行滚动长截图」），再进入会话——视产品对「一步直达」与「防误触」的取舍而定。

**与 GIF/视频 的区分**

- 长截图**不产生**时间轴上的连续媒体，产出仍是**静态位图**；入口放在截屏保存区，与「录一段」类按钮在文案和图标上应**可区分**（例如长图/卷轴类图标 vs 摄像机）。

## 2. 工程师视角：怎么做、拆什么、接哪里

### 2.1 总体流程（通俗版）

1. 用户选定**要截的长内容所在窗口**（或窗口内一块矩形区域）。  
2. 程序把**滚动焦点**放到该窗口（必要时先激活窗口）。  
3. **从顶部或当前位置开始**，每次**向下滚一小段**（或一页），**截一张**当前可见区域。  
4. 重复直到**到底**或**达到上限**或**用户取消**。  
5. 把这一串图交给**合成模块**，输出一张 PNG/WebP 等。

### 2.2 为什么不能「高度相加」就拼完？

因为真实世界里：每次滚动**实际移动的距离**不固定、可能有**动画**、**高 DPI** 下还不是整数像素。若直接用「每张图高度相加」拼接，会出现**错位、重影、断层**。所以**必须**有「算法层」帮我们对齐（见第 3 节），**工程**要把**对齐接口**和**超时/取消**做好。

### 2.3 模块拆分（便于落地）

| 模块 | 职责 | 备注 |
|------|------|------|
| 滚动注入 | 向目标窗口发送滚轮、必要时 PageDown/Home/End | 与平台强相关，宜集中封装 |
| 帧采集 | 复用现有截屏，按固定矩形多次采样 | 与现有 `snap`/capture 对齐坐标系 |
| 会话控制 | 步长、间隔、最大帧数、取消、进度回调 | 避免死循环滚动 |
| 合成服务 | 输入多帧图，输出单图或失败原因 | 内部调用算法（见第 3 节） |
| UI/命令 | 选窗口、预览、保存路径 | 与现有热键/托盘流程一致 |

### 2.4 平台与权限（工程要心里有数）

- **Windows**：常用 `SendInput` 等模拟滚轮；需处理**前台窗口**与**坐标**。  
- **macOS**：除截屏外，滚动注入可能涉及**辅助功能（Accessibility）** 等权限，要提前在文档里写清。  
- **Linux**：桌面环境多样，**行为差异最大**，适合放在后期或分发行版。

### 2.5 与现有仓库的契合方式（概念）

- **Rust 侧**：滚动、合成、会话状态可放在独立子模块，通过 Tauri 命令暴露给前端。  
- **前端**：长截图耗时长，需要**进度条、取消按钮、失败原因**文案，避免「黑盒卡住」。

### 2.6 前端遮罩（Overlay）与长截图：交互与可视化

长截图模式下，要分清两类「滚动」——**背后真实窗口里的内容在滚**（像素来源），和**遮罩上我们自己的 UI 在滚**（多为预览与校对）。遮罩上可以动**巧思**，但**不能**单靠遮罩自己滚动就替代底层内容的滚动（除非换采集路线，例如浏览器 CDP 整页截图，见 §1.5）。

#### 2.6.1 像素从哪来？（先立住前提）

每一帧仍然来自**对屏幕/窗口的截取**。背后应用（浏览器、聊天窗口等）**必须真的发生滚动**，可见区域里的像素才会变，多帧拼接才有意义。遮罩通常是**盖在最上层的透明或半透明层**，**不会自动带着背后的网页一起滚**——除非工程上把滚轮/手势**转发**到目标窗口，或在后台向该窗口注入滚动事件。

#### 2.6.2 遮罩上可以做的几类「巧」

| 类型 | 做什么 | 解决什么问题 | 备注 |
|------|--------|----------------|------|
| **A. 取景框 + 胶片条 / 进度** | 在遮罩上画出**清晰的矩形取景框**（与多次截取的区域一致）；侧边或角上叠**小缩略图条**（每截一帧多一片），像「往长图里加料」 | 用户感知的是**长截图进度**，而不是抽象地「在滚网页」 | 偏 UX，**不改变**采集原理；与现有多显示器/区域遮罩可共用「画框」能力 |
| **B. 遮罩接滚轮 → 转发给目标窗口** | 用户光标在遮罩上（或在不透明白边/侧栏上）滚动时，由前端通知后端，**把滚轮事件投递到已锁定的目标窗口**（或先把光标移到目标区域再模拟滚轮） | 交互入口可以设计成「在长截图模式里滚」，**心理模型统一** | **工程难度与「直接在网页上滚」同类**，需稳定的目标窗口句柄与各平台行为；macOS 等要兼顾权限 |
| **C. 仅预览区可滚** | 遮罩上单独一块**非透明面板**，展示**已对齐条带的纵向拼接预览**，用户只在**这块**里上下滑动查看接缝、决定是否保存 | **校对与成品浏览**；滚的是**我们自己的 Web 内容** | **不替代**底层继续采集时的滚动；采集仍依赖背后窗口内容在动，或由 B 转发 |

三类可以**组合**：例如 A + B（取景框 + 转发滚轮 + 胶片条），或 A + C（自动滚时只显示 A，结束后进入 C 校对）。

#### 2.6.3 与现有多显示器 / 区域遮罩的关系

- 长截图可在同一套遮罩上增加**模式切换**（普通选区截屏 vs 长截图）：同一套坐标与显示器逻辑，多出来的 UI 是**取景框样式、胶片条、专用按钮**（开始 / 暂停 / 结束 / 取消）。  
- **不要**假设「用户只在遮罩内滚动」就能截全长——除非产品明确走 **CDP 等不依赖底层滚动的路线**，那应在架构上与「滚动拼接」**分岔**，避免两套预期混在一套 UI 里说不清。

#### 2.6.4 小结（是否可行）

| 想法 | 结论 |
|------|------|
| 遮罩上画取景框 + 胶片条 / 进度，让过程**可感知** | ✅ 推荐，偏体验与心智模型 |
| 遮罩滚轮**转发**到目标窗口 | ✅ 可行，偏工程，与平台能力绑定 |
| 仅在遮罩内滚**预览条**做校对 | ✅ 可行；**不替代**底层滚动 |
| 只靠遮罩自身滚动、**不滚背后应用**，还想得到「整段内容」 | ❌ 与通用滚动拼接**矛盾**；除非换采集源 |

### 2.7 保存/退出条上的「长截图」控件：工程与交互要点

本节落实 **§1.6** 的入口，便于前端与命令层对齐。

#### 2.7.1 放置与状态

| 要点 | 说明 |
|------|------|
| 位置 | 与 **保存**、**取消/退出** 同一操作区（同一行或同一卡片内），保持「截屏收尾」心智模型统一 |
| 可见性 | 仅在 **截屏流程已激活**（遮罩已显示、选区已确定或可调）时展示；**未进入截屏**时不单独露出长截图，避免误进 |
| 禁用态 | 无有效选区、或当前平台不支持时，按钮 **disabled** 并给出简短原因（tooltip 或副文案） |

#### 2.7.2 与「保存并退出」的关系

- **保存并退出**：输出**当前这一帧**矩形截图，结束会话。  
- **长截图**：进入**新子流程**（多帧 + 合成），成功后再走保存/路径选择；**失败或取消**时应能回到**仍保留选区**的截屏界面，或明确是否丢弃当前帧——产品需在实现前定一条默认策略（建议：**取消长截图 ≠ 退出截屏**，除非用户点「退出」）。

#### 2.7.3 防误触与可发现性

- 图标需 **tooltip**；长截图为 **耗时操作**，可选 **二次确认** 或 **首次使用时轻提示**。  
- 主按钮（保存）与长截图在样式上 **主次分明**（例如主按钮实心、长截图为次要/线框或图标+文字）。

#### 2.7.4 与后端/命令的衔接（概念）

- 前端在「长截图」点击后调用 **独立命令或子状态**（如 `start_long_snap_session`），与单次 `capture` 区分；会话内进度、取消通过 **事件或轮询** 回传，与 §2.5 一致。  
- **选区坐标**从当前截屏 overlay 状态传入，避免用户再选一次。

## 3. 算法视角：对齐、拼接与停止（尽量少公式）

### 3.1 核心问题是什么？

我们手里有**多张**「同一区域、内容略有上下位移」的截图。算法要做的，就是：**算出相邻两张图在竖直方向上相对移动了多少像素**，然后**裁掉重复部分**，再**竖着接起来**。

可以把它想象成：**两张透明胶片叠在一起，上下错开一点，你要找到错开多少像素时，重叠部分最「像」**——这个「像」的程度可以用计算机来比较。

### 3.2 为什么需要「重叠带」？

相邻两帧之间，**下半张图和上一张的下半部分**应该长得像同一段内容。我们只在**重叠区域**里找最佳对齐，比整图搜索更稳、更快。工程上可配置**最小重叠高度**（例如不小于某几十个像素）。

### 3.3 常见做法（由简到繁）

| 层级 | 思路 | 特点 |
|------|------|------|
| **入门（推荐先做）** | 在重叠条带内，对两行像素做**归一化互相关**或**模板匹配**，在一维**偏移量**上搜峰值 | 实现直接、可解释；纵向长截图时**只搜竖直方向**，问题是一维的，相对简单 |
| **进阶** | 用**特征点**（如 ORB）匹配重叠区，求单应性或平移 | 对轻微动态内容更鲁棒，依赖与计算量更大 |
| **融合** | 对齐后，在接缝处做**渐变融合**（alpha 混合），减轻接缝感 | 常与入门方案搭配即可 |

**不需要**一上来就用深度学习；多数工具类产品的长截图，**条带 + 一维搜索 + 融合**已能验证可行性。

### 3.4 算法侧要处理的失败情况

| 现象 | 可能原因 | 处理思路 |
|------|----------|----------|
| 对不齐 | 内容变化大（聊天、Feed） | 检测相似度过低则**中止并提示**，或限制场景 |
| 峰值不明显 | 大面积纯色、无纹理 | 扩大重叠区或提示用户换背景 |
| 接缝明显 | 仅硬拼接，无融合 | 加重叠融合 |
| 超长图内存爆 | 像素过多 | 架构上的**硬上限** + 分块合成策略（工程与算法协同） |

### 3.5 「停止滚动」和算法的关系

**到底了**往往用**图像相似度**辅助判断：若新截一张与上一张几乎一样，可能已滚到底或内容不再变化。  
这与「对齐」用的是**同一套相似度思想**，但**阈值与用途**不同——**对齐**要精确偏移；**停止**只要**粗判**是否还能继续。

## 4. 三视角如何对齐（协作表）

| 维度 | 架构师 | 工程师 | 算法 |
|------|--------|--------|------|
| 首要问题 | 做不做、做到哪、边界与上限 | 模块怎么拆、平台怎么接、怎么取消 | 帧间位移怎么估、怎么拼、何时判失败 |
| 交付物 | 产品边界、演进路线、非功能指标 | 可运行模块、命令、错误码 | 可复现的测试用例与参数建议 |
| 共同约束 | 内存/时长上限、隐私与权限 | 超时、取消、日志 | 与上限匹配的复杂度与分辨率策略 |

**补充**：**呈现与交互（遮罩上的取景框、胶片条、滚轮转发、预览区）** 不单独占一列，统一归在工程侧落地（见 **§2.6**），架构上对应 **§1.3** 的「呈现与交互层」轻量抽象。  
**产品入口（截屏域、保存/退出区）** 见 **§1.6**、**§2.7**。

## 5. 附录：术语小抄

| 术语 | 通俗解释 |
|------|----------|
| 纵向长截图 | 只上下滚、只拼竖直方向，最常见 |
| 取景框 | 遮罩上标出的、与多次截取区域一致的矩形，帮助用户对齐心理模型 |
| 滚轮转发 | 在遮罩上收到滚轮后，由后端把事件转给目标窗口，使「在长截图模式里滚」成立 |
| 胶片条 / 进度条 | 每采一帧叠一小缩略图，可视化长图「已经拼了多长」 |
| 预览区（可滚） | 遮罩上非透明区域，仅用于浏览已拼接结果，不替代底层采集 |
| 重叠带 / 重叠区 | 相邻两帧里应该「长得像」的那一段区域 |
| 互相关 / 模板匹配 | 在重叠区里找「最匹配」的竖直偏移量 |
| 融合 | 接缝处渐变混合，减轻一条硬线 |
| Spike | 用小实验验证「能不能做通」，不写完整产品 |
| 保存/退出区 | 截屏流程末段含保存、取消等操作的界面区域；长截图入口建议放在此区域 |
| 长截图入口 | 进入长截图会话的按钮或图标，与「保存当前帧」并列、主次区分 |
